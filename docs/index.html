Edge SHM Reference Architecture

An open, reproducible design for continuous structural health monitoring (SHM) that runs at the bridge, on low-cost hardware, and keeps working when the network does not.

Most monitoring systems stream raw waveforms to a central server and analyze them later. That design is expensive per bridge, needs a reliable link, and stops working during the events it is meant to catch. This architecture moves the analysis to an edge node at the structure: it ingests continuous sensor streams, compares them against a learned baseline, and sends only compact health summaries and anomaly flags upstream. The design is deliberately hardware-agnostic and vendor-neutral so that a transportation agency, a consulting firm, or a research group can implement it on their own inventory without rebuilding the data-processing layer.

Design goals

1. Process at the source

Continuous windows of sensor data are analyzed on the bridge. End-to-end latency from sample to assessment is well under one second.

2. Transmit summaries, not waveforms

Uplink carries health indicators, trend summaries and anomaly events. Raw data stays in a local ring buffer and is retrievable on demand.

3. Run on commodity hardware

Validated on a 4 GB, general-purpose CPU node. Per-site cost is in the range of a consumer single-board computer, not a server.

4. Stay autonomous

No cloud dependency in the processing path. Loss of connectivity degrades reporting latency, never analysis.

Quickstart

Regenerate every number in the paper from the public datasets. The repository is a research pipeline, not a packaged daemon: it downloads the data, builds the spectrogram caches, fits the detectors, exports per-window results and times the edge node in a resource-limited container.

# 1. Install (Python 3.7+; Docker for the latency step)
git clone https://github.com/LorenYan98/edge-shm-reference-architecture.git
cd edge-shm-reference-architecture
pip install -r requirements.txt
docker build -t shm-edge:py37 docker/

# 2. Fetch the three open datasets from Zenodo (~5 GB, resumable, checksums in data/)
./download.sh && ./download_chillon.sh

# 3. Caches, detectors, evaluation and ViT latency (hours for the ViT trainers; minutes for PCA alone)
./run_v2.sh

# 4. Masked ViT scoring, merge, and PCA latency inside the 4-vCPU / 4 GB container
python3 -m shm.rescore --k-masks 4 && python3 -m shm.merge_rescore
./run_pca_latency.sh
Outputs land in out/ with the same file names as the committed results/, which are the files the paper's build script reads. results/summary.json holds the confusion matrices and AUCs; results/latency_pca_info.json the latency distribution.

Architecture

The system has three planes. The sensing plane is whatever is already on the structure. The edge plane is a single node per structure (or per span group) that runs the processing pipeline. The agency plane receives summaries and feeds existing asset-management workflows. Only the edge plane is prescribed by this architecture; the other two are integration points.

Figure 1. Solid arrows are the always-on path. Dashed arrows are optional inputs (visual channel) and on-demand raw retrieval. Nothing to the right of the edge plane is required for the node to keep assessing the structure.

Uplink and offline operation

The uplink is the only component that touches a network. It publishes three message types: periodic health summaries (compact statistics per window group), anomaly events (score, channels implicated, time range), and trend digests (daily). Raw windows are never streamed by default; an operator can request a specific time range and the node serves it from the local ring buffer. When the link is down, messages are queued on disk and delivered in order on reconnect. Analysis continues at full rate throughout.

Baseline and anomaly model

Operational bridge data rarely contains labeled damage, so the architecture follows the established SHM practice of characterizing normal behavior and flagging departures from it. The baseline is fit on an initial period of healthy operation and refreshed on a schedule to track slow environmental drift. Evaluation therefore reports specificity (how often a healthy structure is correctly called healthy) as the primary metric, because a high false-alarm rate is what makes agencies turn monitoring systems off. Sensitivity to documented structural changes is reported where the dataset includes them.

Benchmarks

All three evaluations use openly licensed monitoring data recorded on in-service bridges, with documented reference periods. The protocol is identical across structures: reference-condition files split 60 / 20 / 20 into train, calibration and test by source file; changed-condition files are test only; one threshold per structure from the calibration split. Latency is measured for the deployed detector at batch size one inside a 4-vCPU, 4 GB, CPU-only container.

Latency

Deployed detector: 59.0 ms mean, 98.9 ms P95, 375 MB peak memory over 1,160 test windows. The 34.3 M-parameter Vision Transformer under the same protocol: AUC 0.905 on KW51, 284 ms mean; it does not exceed the linear detector. A centralized pilot reported 18 to 67 seconds for transport alone before analysis began.

What the third row means

Vänersborg is kept as a scoped negative result: a generic spectrogram detector on the available channels does not see a local fracture in one member. The protocol was not tuned to make it pass. The paper discusses the bound this places on structure-agnostic detection.
